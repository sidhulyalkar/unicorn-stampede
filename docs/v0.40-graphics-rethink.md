# v0.40 graphics rethink

## Baseline

This branch starts from `main` after the qualified v0.37 gameplay/onboarding promotion. The experimental procedural-graphics stack in PRs #13-#17 is intentionally **not** inherited.

The goal is not to make the town denser by adding more shapes. The goal is to make the existing town read as a coherent place with stronger depth, architectural identity and gameplay clarity for the same or fewer packed bytes.

## What failed in the previous art stack

The rejected screenshot exposed a useful failure mode:

- generic buildings became too similar in silhouette and material;
- large black nameplates did most of the semantic work;
- repeated pastel window bars made buildings feel like UI cards rather than architecture;
- greenery, roads and buildings sat on nearly the same visual plane;
- procedural variation increased state count without increasing perceived authorship;
- additional details competed with the already-strong unicorn trails, paint and HUD.

The lesson is that **state count is not visual quality**. A procedural grammar must improve hierarchy, silhouette and material separation before it earns additional variation.

## New art doctrine

### 1. Preserve the gameplay silhouette

The player must instantly read:

1. unicorns and their control state;
2. powerups / distractions;
3. destructible structures and landmarks;
4. roads / navigable space;
5. decorative environment.

Environmental detail must remain lower contrast than gameplay signals.

### 2. Architecture before decoration

A generic building should be recognizable from three inexpensive layers:

```text
lot / shadow
    ↓
wall + roof mass
    ↓
facade punctuation
```

Do not bolt on a prop catalogue.

### 3. Text is reinforcement, not identity

The large black sign bar should be treated as a candidate for compression recovery. Generic buildings should increasingly identify themselves through facade structure; strong text labels are reserved for landmarks or contextual proximity.

### 4. One deterministic genome, few high-information outputs

Existing object data such as family, x/y position, hue and district may drive a small number of correlated decisions:

- roof silhouette;
- facade rhythm;
- storefront depth;
- lot edge / apron;
- one micro-detail.

Do not create independent random decisions for every feature. Correlated variation looks designed and compresses better.

### 5. Improve the whole screen before increasing local detail

A change is successful only if the full gameplay screenshot is better, not merely a zoomed-in building.

## First research ladder

### A. Sign simplification / removal

Measure variants that shrink or remove the generic dark sign plate while preserving landmark labels. Recovered bytes can finance architecture that remains visible at gameplay zoom.

Questions:
- Can family identity survive without the plate?
- Is text still readable under trails and paint?
- Does the town immediately look less like a grid of UI cards?

### B. Massing grammar

Keep the current building footprint but test 3-4 silhouette cues derived from family:

- civic / centered roof;
- storefront canopy;
- masonry parapet;
- greenhouse / light roof.

Prefer one shared path with parameters over bespoke branches.

### C. Material hierarchy

Separate:

- ground;
- lot/apron;
- wall body;
- roof/trim;
- windows.

Use luminance and saturation hierarchy rather than adding texture noise.

### D. Lot grounding

Only after the facade is stronger, test tiny non-gameplay lot cues such as:

- narrow sidewalk pad;
- side service strip;
- small parking rhythm;
- planted frontage represented by muted rectangles, never gameplay flowers.

### E. Landmark pass

Upgrade Bakery, Market, Greenhouse, Clock Tower and Town Hall only after generic architecture is stable. Landmarks should be visually exceptional, not merely larger labels.

## Explicit non-goals for the first tranche

- no road-topology changes;
- no new gameplay objects;
- no decorative `flowers`;
- no procedural map reflection;
- no additional particle systems;
- no runtime RNG for graphics;
- no dense texture simulation;
- no spending the entire 13k reserve on ornament.

## Evaluation contract

Every candidate should be judged on four axes.

### Visual hierarchy

At normal gameplay zoom:
- unicorns remain the highest-salience moving elements;
- powerups remain obvious;
- buildings feel grounded and dimensional;
- labels do not dominate the town;
- roads remain readable beneath paint.

### Architectural identity

Without reading text, a viewer should be able to distinguish at least the major building families by massing/facade cues.

### Compression

Use paired Terser -> Roadroller -> ZIP comparisons against the exact `main` baseline. Source-byte reductions are evidence only when the final archive also improves.

Do not promote a candidate from a single Roadroller result. Repeat any apparent win.

### Safety

Rendering must not mutate gameplay state or introduce RNG consumption, collision objects, distractions, powerups, landmark placement, road geometry or scoring changes.

## Promotion rule

Do not modify the production renderer with a broad art rewrite first.

1. isolate a single visual question;
2. benchmark candidate replacements;
3. select a visual + compressed Pareto winner;
4. integrate only that winner;
5. run the complete gameplay / packed-runtime suite;
6. inspect a full-screen gameplay capture;
7. only then begin the next visual layer.

The target is **fewer visual systems, stronger consequences**.

## Initial hypothesis

The highest-value first experiment is likely the generic sign plate. It is visually dominant and source-expensive. If we can reduce it while making family architecture carry more identity, we can simultaneously recover byte budget and move the town away from the flat card-grid aesthetic.
