# v0.38 road-edge grammar

## Research question

Can the existing road + crosswalk renderer be reorganized so richer street-edge detail costs zero or negative packed bytes?

The target is not to spend v0.37's remaining reserve. The target is to recover bytes by making one road grammar do more jobs.

## Current vocabulary

Each road rectangle currently owns:

- dark asphalt fill;
- dashed gold centerline;
- canonical crosswalks rendered separately at the six known intersections.

The v0.38 hypothesis is that repeated edge rhythm can visually imply curbs / parking / service boundaries if it shares the same dash state already required by the centerline.

## Compression discovery: orientation is geometry, not control flow

The current centerline renderer branches between horizontal and vertical roads. But orientation is already encoded by the rectangle dimensions. Let:

```text
v = width < height
```

Then the centerline start can be written as:

```text
x0 = x + v * width/2
y0 = y + !v * height/2
```

and the end as:

```text
x1 = x0 + !v * width
y1 = y0 + v * height
```

This removes the horizontal/vertical drawing branches while preserving the same centerline geometry. At source level, the road + crosswalk candidate drops roughly 59 bytes before compression.

More interestingly, a single three-state loop over edge position `[0,.5,1]` can draw **left/top edge + centerline + right/bottom edge** using the same equations and same dashed stroke. That version is still roughly 32 source bytes smaller than the original road/crosswalk renderer while adding two contextual road-edge rhythms.

This is exactly the kind of grammar we want: the visual detail emerges from a more general geometric representation rather than an appended prop system.

## Candidate ladder

1. `control`
   - exact v0.37 renderer.
2. `cross-golf`
   - replace the two explicit crosswalk `fillRect` calls with a two-row loop.
   - first paired evidence: control 13,250 vs cross-golf 13,253, so **-13 source bytes did not translate into packed savings**.
3. `arith-center`
   - crosswalk loop plus branchless centerline geometry derived from road orientation.
   - expected to be the pure compression candidate.
4. `parallel-edge`
   - same branchless geometry;
   - iterate edge position `[0,.5,1]` so the exact same path grammar draws two road-edge rhythms plus the centerline.
   - this is the preferred visual candidate if its packed delta stays at or below control.

An earlier exploratory run tested wrapper-style edge strokes, but that run exposed a missing statement terminator in the temporary benchmark transform after successfully measuring control and cross-golf. The benchmark now syntax-checks every transformed renderer before invoking the packer, so candidate failures cannot masquerade as compression results.

## Safety contract

This tranche is renderer-only research. It may not change:

- `roads` geometry;
- traffic lanes;
- crosswalk coordinates;
- collision geometry;
- district boundaries;
- landmarks, powerups, flowers, people or unicorn state.

A promoted runtime candidate must keep the v0.36 topology smoke and v0.37 render-purity smoke green.

## Compression rule

Judge candidates by same-workflow paired ZIP delta, not JavaScript character count. Roadroller may vary modestly between runs, so tiny single-digit differences should be replicated before promotion.

A detail is especially attractive if it uses an already-live drawing state. Reusing one dash pattern and one material is preferable to adding a new mini rendering subsystem.

## Promotion target

Prefer a candidate that:

1. is no larger than the paired control, or is clearly smaller;
2. gives the roads visibly embedded edges rather than floating gray bands;
3. does not make intersection markings compete with gameplay cues;
4. retains useful reserve under the 13,312-byte cap;
5. keeps all gameplay and renderer-purity tests green.

If no candidate satisfies those gates, preserve v0.37 and treat the benchmark as a negative result rather than spending reserve for decoration.
